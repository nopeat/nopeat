# Architecture

How Nopeat is put together, and why it is built this way. Written for someone who
knows JavaScript or TypeScript and is about to read the Rust.

## The shape

Four crates. The dependency only ever points one way.

```
nopeat-core      the model and the engine. No IO, no CLI, no async, no unsafe.
  ├── stats      streaming ingest of stats.json / metafile.json
  ├── folder     a build directory with no bundler metadata
  ├── sizes      measured parsed + gzip bytes per asset
  ├── sourcemap  source map v3 -> decoded segments
  ├── fusion     the join; ghost and hidden classification
  ├── manifest   framework manifests (Next, Nuxt, SvelteKit)
  ├── report     graph -> HTML / JSON / CSV
  └── model      UnifiedBundleGraph and everything in it
nopeat-cli       argument parsing, budgets, the HTTP server, exit codes
nopeat-wasm      the core behind a browser build
```

`nopeat-core` performs no IO and is built with `#![forbid(unsafe_code)]`. Bytes
enter through `model` or an `ingest_*` constructor; nothing in the engine touches
the filesystem. That is why the whole engine is testable with no fixtures on disk
and no temporary directories, and why there is no hand-written SIMD anywhere in
it: the bottleneck was never arithmetic, it was allocation and IO.

## The pipeline

Data moves through six stages. Each answers one question, hands the next an
answer, and does not reach backwards.

```
        bytes in                        UnifiedBundleGraph                    payload out
             │                                   │                                 │
  ┌──────────┴───────────┐           ┌───────────┴───────────┐          ┌───────┴───────┐
  │ 1  ingest            │           │ 4  fusion             │          │ 6  report     │
  │  stats / folder      │──────────▶│  the join              │─────────▶│  HTML/JSON/CSV│
  └──────────────────────┘           │  ghost / hidden       │          └───────────────┘
                                     └───────────┬───────────┘
       ┌─────────────────────────┐  ┌────────────┴────────────┐
       │ 2  sizes                 │◀─│ 3  sourcemap            │
       │  parsed + gzip, rayon   │  │  VLQ, index sections    │
       └─────────────────────────┘  └─────────────────────────┘
```

**1. Ingest.** Two entry points, because there are two kinds of input. `stats`
reads a declared module graph — webpack and rspack `stats.json`, esbuild
`metafile.json` — and answers *what did the bundler say it put in the bundle*.
`folder` reads a build directory, which is all Vite, Rollup, Parcel and tsup emit
by default, and answers *what is actually on disk*. Both produce the same graph;
the graph records which sources it had.

**2. Sizes.** `stat` is what the bundler claimed. `parsed` is what the file
weighs. `gzip` is what it weighs compressed. They disagree, sometimes a lot, and
the disagreement is usually the interesting part: `stat` is uncompressed source
weight, `parsed` includes minification and the bundler's own runtime. Assets are
measured in parallel with rayon, because each is an independent file read plus a
gzip pass.

**3. Source maps.** A v3 map decoded to segments, with indexed map sections and
tail attribution: bytes after the last mapping are credited to the last source
rather than dropped. Paths are normalised, because bundlers emit `\` on Windows
and `file://` URLs and bare relative paths in the same build.

**4. Fusion.** The join. `webpack-bundle-analyzer` reads a graph,
`source-map-explorer` reads a map, and nobody reconciles the two. For each source,
fold its byte share into the modules that produced it and correct each module's
size to ground truth. What does not reconcile becomes a diagnostic: **ghost
code**, declared by the bundler and mapped by nothing, and **hidden code**,
generated bytes that map back to no module.

Ghost code is only definable against a declared graph, so a bare build folder
reports it as undetectable (`NPT0051`) rather than as a reassuring zero.

**5. Budgets.** A limit on `total`, a `chunk` or a `package`, optionally on a
named dimension. A breach exits 1. A rule that matches nothing is an error, not a
silent pass — a typo in a config must not quietly pass CI. Neither may a config
that omits `limits` entirely.

**6. Report.** A self-contained HTML file: Canvas 2D squarified treemap, three
grouping dimensions, fuzzy search, light/dark/auto, no web fonts and no network
requests. Plus `--mode json` and `--mode csv`.

## The techniques

Four, and each has a number behind it. The full records are in
[`bench/results/`](bench/results/), measured per
[`docs/schema/bench-spec.md`](docs/schema/bench-spec.md).

### Streaming ingest, not a parse tree

Deserialise module by module through a `DeserializeSeed` rather than building a
`serde_json::Value` and walking it. A `Value` is a tree of boxed maps and owned
strings; on the 1 GB fixture it cost about 550 MB before any analysis started,
against a 400 MB ceiling. Modules enter the graph as they arrive, so the document
is never resident.

Ingest is deliberately **serial**. One sequential file read parallelises badly:
farming chunks out to threads means buffering them, which spends the memory
streaming exists to save. The parallelism is downstream, where the units are
genuinely independent.

### Build the index, do not scan

Matching each module to its source was O(modules × sources): 2.5 billion
comparisons, 73.8 s on the fused benchmark. A suffix index built once per asset
makes the lookup a hash, and the same benchmark drops to 4.94 s. A property test
asserts the index and the original scan agree, including on the awkward cases, so
it is the same rule with a lookup table rather than a second implementation of it.

### Intern what repeats

A large build has hundreds of thousands of modules and a few hundred packages.
Package references are interned, so every module in a package shares one
allocation. On the 1 GB fixture that was worth about 70 MB.

### Bounded samples, not truncated lies

`ghost_modules` used to hold one entry per unmapped module — 445,602 of them,
47 MB, for something documented as a summary. It is now a bounded sample that
reports what it dropped; the counts stay exact. The hidden byte total was also
being summed *after* truncation, so it under-reported.

A related trap: an earlier figure connected the ghost samples into a line and
drew a fall that was never measured, because two different benchmarks shared an x
coordinate. The figure is markers and no line, for that reason.

## Decisions

| decision | evidence |
|---|---|
| streaming JSON, not `simd-json` | `simd-json` needs the whole document in memory, which is the ceiling being removed |
| our own HTML report, no vendored viewer | a viewer we do not control cannot show fusion data without a fork |
| rayon for size and gzip work | 25,600 assets: 2,177 ms serial → 342 ms. The parse was never the bottleneck |
| a suffix index for the join | 2.5 billion comparisons → 4.9 s |
| exact counts, bounded lists | one entry per unmapped module cost 47 MB for a field documented as a *summary* |
| property tests over fixtures | found two defects no fixture could see: sizes never scaled **down**, and an out-of-range source index made attribution vanish silently |
| no `unsafe`, anywhere | the bottleneck was allocation and IO, neither of which unsafe addresses |
| no WebGL treemap yet | 10k nodes is fine on Canvas 2D; the swap is later, behind a stable payload |

Targets that were not met are recorded as unmet rather than dropped: B2 (1 GB
ingest-only, target 3 s, measured 4.40 s) and B10 (browser first paint and
interaction) are both listed that way in `CHANGELOG.md`.

## Invariants

Two hold everywhere, and both are enforced rather than documented.

- `check_size_invariant` gates every write to the graph. A module's effective size
  is derived, never assigned independently.
- Totals are recomputed after every mutation, so a report cannot carry a stale
  rollup.

## Diagnostics

Every diagnostic the tool can emit, and the condition that produces it. Each code
is a stable string: grep for it.

| code | severity | condition |
|---|---|---|
| `NPT0001` | warning | the stats file has no `modules` array, which is a dev-server export rather than a build |
| `NPT0002` | error | no asset was found next to the metadata, so there is nothing to attribute |
| `NPT0040` | error | a budget rule was breached; the command exits 1 |
| `NPT0042` | error | a source map failed to parse. The map is named, because a silently dropped map shows up as a lower coverage figure that reads like a build that shipped no maps |
| `NPT0050` | warning | no source maps sit next to the output, so only file sizes are known. Build with `--sourcemap` for per-source attribution |
| `NPT0051` | info | no bundler metadata in the folder, so ghost code cannot be detected. It needs a declared graph to compare against |
| `NPT0052` | info | modules with no name were skipped. webpack emits one for its runtime, and a module with no path cannot be attributed to a file |
| `NPT0060` | info | modules below `--min-size` were filtered out. The count and the bytes are exact; the names listed are a sample |

## The payload

`docs/schema/unified-graph.md` declares the graph, and
`docs/schema/report-schema.json` the report. `docs/schema/cli-surface.md` is the
CLI. `docs/schema/bench-spec.md` is how a measurement has to be taken for a
number to be publishable.
